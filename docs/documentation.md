# 文档维护规则

## 内容分工

| 文档 | 维护内容 |
| --- | --- |
| 根 README | 产品简介、安装、运行与文档入口 |
| AGENTS.md | 协作边界和必须遵守的规则 |
| PRODUCT.md / DESIGN.md | 产品原则 / 设计语言与真实 token 来源 |
| docs/ | 工程架构、契约、开发及验证 |
| 官网 docs / en | 使用与开发任务的中英文指南，同 slug |
| 官网 blog | 应用开发的历史决策与实际验证；不写官网改版日志 |
| mcp/README.md | 外部 MCP 安装、工具与信任边界 |
| 产品页 README | 站点内容、布局边界、构建和生成产物 |

## 写法

参考 [Google 开发者文档风格指南](https://developers.google.com/style/highlights)：用直接、具体的句子说明任务，前提放在步骤前，顺序操作用编号列表，代码用代码字体，链接说明目标。英文标题使用 sentence case。中文版保持自然中文，不把界面一半写中文一半写英文。

每篇任务文档回答：适用于谁、需要什么、怎么操作、结果是什么、失败怎么办、如何验证。技术标识和作者 TeX 源码保持原样。未知平台、未签名包和近似 SyncTeX 映射需要说清，不写没有证据的性能、兼容性或隐私承诺。

不固化行数、IPC 数量、测试条数、面板数量和安装包数量作为维护契约。需要统计时给出查询方法或注明历史日期。测试报告和博客中的历史数字保留历史语境，不冒充当前状态。

## 官网同步

官网篇目保持 slug 和站内链接稳定；中文放 `product-page/src/content/docs/*.md`，英文放 `en/` 同名文件。front matter 包含 slug、title、group、order、summary。只用站点解析器支持的标题、段落、列表、代码块、引用、表格和行内标记，不写 Mermaid、HTML 或复杂嵌套列表。

内容自动被 glob 加载，不需要改路由、组件、依赖或布局基线。先后运行 `pnpm check:layout`，再运行类型检查与构建。生成的 feed、llms、sitemap 和 robots 由 Vite 生命周期调用脚本生成，不手改。修改生成器需要单独核对发布范围；只更新内容不授权改页面设计。

## 审计和接手

旧审计要保留日期，增加后续核对状态与源码依据；不能长期把已修复事项放在当前待办。新会话先看 `docs/README.md`，然后按任务阅读，避免一次加载全部博客和截图。

公开规范与产品文档可以进入 Git。私人聊天、凭据、superpowers 计划及临时验收记录不可提交。生成产物只按现有站点约定维护，不把缓存、dist 或本地环境文件混入。
