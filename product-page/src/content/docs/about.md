## TeXPro 是什么

TeXPro 是一个面向 LaTeX 的桌面写作工作台。它把源码编辑器、可视写作层、PDF 预览、工程管理与编译链放在同一个窗口里，让你从写第一行到交出 PDF 都不必离开应用。

它不替代 LaTeX，也不隐藏 LaTeX。文件仍然是 `.tex`，编译仍然由本机的 latexmk 与 TeX 发行版完成；TeXPro 做的是把这条链路变得连贯：编辑时看得懂结构，编译后对得上位置，交付前查得清问题。

仓库名沿用 `TexStudioPro`，产品名是 TeXPro。它与 TeXstudio、Typora 等项目没有隶属关系。

## 为谁而做

TeXPro 主要面向三类人：

- 写论文的研究者与研究生：多文件工程、参考文献、交叉引用、期刊模板
- 做课程作业或中文排版的学生：需要公式、图表与稳定的中文支持
- 维护技术文档的作者：长文、代码、表格与多次修订

共同点是：他们愿意为排版质量付出学习成本，但不想把时间花在工具切换与格式修补上。

## 设计哲学

下面七条不是口号，而是出现冲突时的排序依据。

- **写作必须连续**：正文、公式、表格、乐谱、电路图都处在同一条光标流里。日常输入与修改不应该先打开工作室、填一张表单，再点「完成」。
- **源码是记录**：`.tex` 是唯一事实来源，可视层只是它的投影。源文件必须保持可读、可移植、可离线编译，不能变成某个应用私有的文档格式。
- **帮助按需出现**：只有你选中内容或明确请求时，工具才出现。把配置表单搬进正文，不等于连续写作；工作室是可选的加速器，不是默认路径。
- **保留作者的位置**：预览刷新、校验、插入宏包、后台编译都不能抢走当前文件、光标、选区、撤销历史与滚动位置。输入法还在组合时，界面不能抢先重排。
- **闭环**：写作、工程结构、编译诊断、PDF、引用与版本历史应当在同一个工作区里相遇，并且共享同一个主文件。
- **自动化可检查**：AI、MCP、自定义构建与备份要让人看得见它们做了什么，并且可以撤销。
- **本地优先，远程显式**：工程默认留在磁盘上；联网、云与协作都是带有可见边界的选择。

发生冲突时，优先级从高到低是：连续写作、源码可信、可视化完整、工具数量。

## 设计语言

视觉目标可以概括为「纸面正文，安静外壳」：阅读区接近纸张，周围界面退到背景里。

| 元素 | 取值 | 用意 |
| --- | --- | --- |
| 编辑纸面 | 主题变量 `--paper` | 纸张色而非纯白，减少屏幕反光 |
| 正文颜色 | `#2b2926` | 比纯黑柔和，长文阅读不刺眼 |
| 强调色 | 暖陶土色（Studio `#d97757`，Paper `#b4532a`） | 只标记焦点、选中与当前状态 |
| 正文宽度 | `760 px` | 单栏，控制行长 |
| 正文字号 | `18 px` | 屏幕阅读的舒适区 |
| 圆角 | `10 px` | 柔和但不过度，不卡通化 |

字体分三套：界面用 SF Pro、苹方或系统无衬线；正文用 New York、Charter、宋体类或 Georgia；代码用 SF Mono、JetBrains Mono 等等宽字体。三套字体各司其职，不混用。

- 图标统一用 Lucide 的线性图标，保持同一笔画粗细；功能入口不靠彩色表情符号区分。
- 动效只用于面板进出与状态转换，并遵循系统的「减少动态效果」设置；没有装饰性动画。
- 主题提供 Studio、Night 与 Paper 三套。切换主题改变颜色与明暗，不改变版式、字号层级与强调色的含义。

## 交互思路

交互的目标是让手不离开键盘，眼睛不离开正文。

- **键盘优先**：常用动作都有快捷键或命令面板入口，鼠标是加速器而不是前提。完整列表见 `/docs/shortcuts`。
- **就地编辑**：段落、公式、表格与图片都在原位修改。选中文本时只浮出六个动作——粗体、斜体、代码、行内公式、引用、交叉引用，不打开大面板。
- **进出明确**：可视块里按 Esc 回到源码；关闭写作辅助器时恢复原来的光标与选区，不把半成品留在文档里。
- **位置保持**：自动保存、后台编译与预览刷新不抢焦点，不重置选区；输入法组合期间不打断输入。
- **可见的自动化**：AI 的修改建议以动作卡片列出，逐条 Apply 才写入；构建使用你配置的命令，shell-escape 默认关闭。没有静默改写。
- **素材即写即得**：拖入或粘贴图片会存进工程的素材目录，并插入带标签的 figure；SVG 会先转成 1800 px 的 PNG。
- **反馈克制**：成功用短提示，错误进 Problems 与日志；删除、替换全文这类破坏性操作会先确认，其余时候不打断写作。

判断交互好坏的标准不是动画是否顺滑，而是写完一段之后需不需要重新找光标。

## 不做什么

### 不做在线协作平台

TeXPro 有基于 Yjs 的局域网协作，但它不是云端文档服务：没有房间托管、没有公网分享、没有账号权限体系。需要多人远程协作时，继续用 Overleaf 或 Git，TeXPro 只负责本地编辑与版本衔接。

### 不做 Markdown 编辑器

Markdown 与 Typst 只作为导入、导出的互操作格式存在。TeXPro 的源文件是 LaTeX；如果目标是 Markdown 写作，应该选择专门的 Markdown 工具，而不是在这里绕一圈。

### 不做玻璃拟态

界面刻意避免 Liquid Glass 式的半透明、强反光与层层模糊。视觉语言接近纸张与印刷：稳定的底色、清晰的层级、少量强调色。这不是审美偏好，而是为了让长时间阅读与写作不累。

## 技术栈

| 层 | 选择 | 说明 |
| --- | --- | --- |
| 桌面运行时 | Electron 44 | 原生菜单、文件系统与子进程 |
| 渲染层 | React 19 + TypeScript 5.9 | 编辑器、面板与状态 |
| 构建 | Vite 8 | 开发服务器与生产构建 |
| 编辑器 | CodeMirror 6 | 语法高亮、补全、折叠与协作扩展 |
| PDF | PDF.js 6 | 渲染、文本层与反向定位 |
| 公式 | KaTeX 0.19 | 可视层与导出页面的公式预览 |
| 协作 | Yjs 13 | 局域网 CRDT 同步 |
| 图标 | Lucide | 界面图标 |

进程边界是明确的：渲染层只负责编辑与展示，文件读写、编译进程、密钥加密都由主进程通过 preload 暴露的类型化 IPC 完成。TeX 本身不随应用分发，需要本机安装 TeX Live 或 MacTeX；Node.js 22+ 只在开发时需要。

## 版本与发布节奏

实际下载版本以 GitHub Release 和官网版本页为准，应用基础版本由根 package 文件管理。应用采用夜间构建：GitHub Actions 每天 `13:23 UTC`（Asia/Shanghai 21:23）检查 `main` 相对上一次成功 Nightly 是否有新提交，有则运行回归测试、类型检查与构建，并把安装包发布为 `v{基础版本}-YYYYMMDD-Nightly` 日期预发布。

| 平台 | 产物 |
| --- | --- |
| macOS | 通用 DMG 与 ZIP（Apple Silicon / Intel） |
| Windows | x64 NSIS 安装包、便携版与 ZIP |
| Linux | x64 deb、AppImage 与 rpm |

几点现实约束：

- 自上次成功 Nightly 没有新提交，就不会有新构建
- 夜间构建未签名，macOS 可能提示「无法验证开发者」，Windows 可能触发 SmartScreen
- 构建失败时不会产出安装包，以下载页显示的最新产物为准
- 目前没有固定的稳定版节奏；重要工作请保留自己的备份与版本记录

### 升级与兼容性

`0.1.0` 仍处在快速迭代期，尚未承诺稳定的数据格式。夜间构建可能调整 `.texpro/project.json` 字段、历史与模板结构、导出结果或快捷键。

- 升级前备份整个工程目录，并保留一份已知可用的应用版本
- 先在副本上打开与编译，确认无误后再替换工作目录；不要假设旧版本能读懂新版本写入的数据

## 项目故事

TeXPro 的第一次提交在 2026 年 10 月 21 日，提交信息是「Initial commit: TeXPro visual LaTeX workbench」。它起初不是要做一个全能 IDE，而是想解决一个具体的别扭：TeXstudio 的工程能力很强，但写作时像在终端里排版；Typora 的纸面很安静，却不是 LaTeX 工具。

最初的几天里，仓库很快长出了研究流程、夜间打包、受审批约束的 MCP 与协作编辑；随后是正文内乐谱，以及一份把「连续写作」写成产品契约的文档。这些功能看起来分散，背后是同一条线：所有辅助能力都要回到同一个光标位置。

项目也做过减法。半透明的 Liquid Glass 外壳曾经实现过，后来被完整移除；除非有新的明确决定，它不会回来。LaTeX 语法高亮库 `codemirror-lang-latex` 也没有被采用，因为它是 AGPL-3.0-or-later，与仓库偏好的 MIT 许可不一致。

到今天，它仍然是一个 `0.1.0` 的项目：历史很短，边界还在收敛，夜间构建每天从 `main` 出发。它不假装成熟，但尽量把每个取舍写下来，让后来的人知道为什么是这样。

## 如何参与

### 报告问题

在 GitHub Issues 中描述现象、复现步骤与期望结果。有用的信息包括：

- 版本号与构建日期（页脚或关于窗口）
- 操作系统与 TeX 发行版（TeX Live / MacTeX 的版本）
- 最小可复现的 `.tex` 片段，或工程结构说明
- 编译日志中的关键错误行

不要粘贴 API 密钥、未公开稿件或他人的个人信息。

### 提交代码

欢迎 PR，但请保持改动聚焦：

- 先开 Issue 讨论较大改动，避免写完才发现方向不对
- 遵守渲染层与主进程的边界，不在渲染层直接读文件或起进程
- 行为变更附带测试；至少跑一遍现有测试与类型检查
- 新增依赖前说明理由，优先选择与 MIT 兼容的许可

### 改进文档

产品页文档在 `product-page/src/content/docs/`，每个文件是一个页面，front matter 决定标题、分组与顺序。写作时请：

- 事实以源码与仓库文档为准，不写未实现的功能
- 用 `##` 与 `###` 组织内容，表格与提示按现有页面的写法
- 中文与西文之间留空格，站内路径写作 `/docs/xxx`
